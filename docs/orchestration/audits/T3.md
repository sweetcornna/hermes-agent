## 致命

### F-01 短连接触发条件不能排除 Hermes 正在启动或已重启
`T3-design.md:200-206,257-263`｜核验点 2、3

「状态文件陈旧 + 记录的 PID 已死」不是足够窄的 Hermes 死亡判据。失败时序：旧 `gateway_state.json`
仍记录已退出的 PID → systemd 已拉起新 Hermes 但尚未完成首次状态写入（或写入因权限/磁盘/路径失败）
→ 哨兵判定 writer 已死并开短连接 → 新 Hermes 随后建立自己的持久 WS。**两条连接同时存在，
违反设计自身「零第二连接」的铁律。** 文件缺失、JSON 暂时不可读、旧 PID 未被覆盖时同理。
`PROBE_MIN_INTERVAL_SECS=300` 只限重复频率，消除不了第一次重叠。

修：引入独立的 gateway 运行代际/锁持有证明；任何当前 gateway 进程或运行锁存在时绝不开探针；
对「旧 PID 已死、新 PID 未写入」设启动宽限期 + 连续多拍确认。
**若构造不出不与新 Hermes 竞态的判据，就删掉自动短探针**——宁可把该区间记为删失。
写成测试：旧状态文件 + 新 Hermes 已启动未刷新时，断言探针调用次数为 0。

## 高

### F-02 接口白名单只是常量，实际调用路径没有强制
`T3-design.md:612-629,208-217`；`tools/onebot_client.py:57-65,113-138,146-181`｜核验点 1、3、7

`PROBE_ACTION_ALLOWLIST = ("get_status",)` 没有传入 `onebot_call()` 也没有调用前后校验；
`onebot_call()` 接受任意 action；**`onebot_base_url()` 优先使用 `ONEBOT_HTTP_URL`**，
而设计声称探针只走 `ws://127.0.0.1:3011`；`NET_EGRESS_ALLOWLIST` 只是字面量元组，不限制实际目的地。
⇒ 环境里只要存在 `ONEBOT_HTTP_URL`，所谓 WS-only 探针就变成 HTTP POST 到别处。

修：实现唯一的 `probe_get_status()` 封装而非直接暴露 `onebot_call()`——硬编码拒绝非 `get_status`；
拒绝任何非空 `ONEBOT_HTTP_URL`；严格校验 scheme / 主机 `127.0.0.1` / 端口 `3011`；
对 URL 与动作做**运行时**断言而非只断言常量字面值；egress 限制从「可选推荐」提升为必选部署条件。

### F-03 静态扫描不是权限边界，存在直接绕过
`T3-design.md:694-712`｜核验点 1、3

`FORBIDDEN_TOKENS` 是大小写敏感的源码子串扫描，且允许对含 `SUBPROCESS_ALLOWLIST` 的整行豁免。
绕过示例：`getattr(__import__("os"), "sy"+"stem")(...)`、`__import__("sub"+"process").run(...)`、
`importlib.import_module()`、拆分/改大小写、`os.kill`/`signal`/`ctypes`/裸 socket。
`tests/ops/test_qq_sentinel_boundary.py` 只扫 `ops/qq_sentinel/**/*.py`，覆盖不到被 import 的
`tools/onebot_client.py`、systemd unit 或外部 helper。

修：不豁免整行，只允许一个专用固定实现的 subprocess helper；把 systemd unit 与所有被 import 的
本地代码纳入范围。**保留静态扫描作为防回归检查，但不要称它为权限强制层。**

> **主线程调整**：本条降为「表述问题」而非重新设计。静态扫描面对的是未来的我们，不是攻击者；
> 采纳审计员自己最后那条建议即可。真正的强制层是 F-02 的运行时封装 + systemd 沙箱。

### F-04 `writer_alive` 对现有 PID 语义描述不准，且未处理未来时间戳
`T3-design.md:163-176,250-263`；`gateway/status.py:1168-1188,1716-1722`｜核验点 4、5

设计写成「PID 存活且 `start_time` 匹配」，但 `runtime_status_pid_is_live()` 只在
`recorded_start is not None and current_start is not None` 时才比对；**任一缺失则任何存活 PID
都判为活着**。该函数也不校验 `kind` 或命令行是否真是 Hermes gateway。
另：`_marker_is_stale()` 对未来时间戳 `age` 为负 → 返回非 stale，设计未定义该情形。

⇒ `start_time: null` + PID 复用到别的进程 ⇒ 哨兵认定 writer 还活着，**不发 `OBSERVER_DOWN`**（漏报）。
卡死的 gateway 留下未来 `updated_at` ⇒ 长期不再写入也被判新鲜。

修：写出完整 truth table（PID 缺失 / 进程不存在 / 任一 start time 缺失 / 不匹配 / 进程身份不符）；
缺失或无法验证身份应保守判为「无法证明 writer 存活」，但**随后必须禁止自动探针**以免重触 F-01；
校验 gateway `kind` 或独立运行代际；明确未来 `updated_at` 的容忍窗口；契约测试覆盖这三种边界。

### F-05 24 小时 source-format 闩锁与进程代际无关，同时造成误报与漏报
`T3-design.md:292-310,359-366,473-512`；`gateway/run.py:12723-12733`；`adapter.py:1987-2017`｜核验点 5、6

担心是真实的（`run.py:12732` 确实写 `error_message=None`），但闩锁只记时间，不绑
`(pid, start_time)` 或 adapter 代际：

1. modern 跑过后**回滚到旧 adapter**，24h 内旧 adapter 的陈旧文件仍判 modern → 180s 后误报 `OBSERVER_DOWN`。
2. modern 的 health loop **卡死超过 24h** → 闩锁过期 → writer 仍活 → 陈旧状态重判 legacy →
   进入 `SOURCE_INCOMPATIBLE`，modern 的 observer-down 检测被关闭。**哨兵在最需要时闭嘴。**
3. 没有 `SOURCE_INCOMPATIBLE_CONFIRM_TICKS`。§4.3 声称所有类别都要连续确认，但常量表只定义了
   auth/link/observer/recover；fresh install 或闩锁过期后单次 `error_message=None` 就能触发 A0。

修：闩锁绑定当前平台条目的 writer PID/start_time，或让 adapter 写明确的 schema/version 字段；
新 gateway 代际开始时用独立的「格式未知」状态，不把旧代际的 modern 证据继承给新进程；
给 A0 定义连续确认拍数；**source-format 判定不得覆盖 writer liveness**。

### F-06 账本按原始采样切段，未用告警去抖；`link_down` 被错误当成非删失结束
`T3-design.md:341-344,789-812`｜核验点 12

区间定义为连续 `AccountView == ONLINE` 的极大段，但 10 拍 / 3 拍去抖**只用于发送、不用于账本**。
且 `end_reason=link_down` 定义为结束，而删失规则只覆盖 `observer_down`/`planned_stop`/legacy
⇒ link-down 区间进入中位数。

⇒ `run.py` 的多写者竞态让 `connecting`/`connected` 短暂覆盖时，告警吸收了抖动但账本制造假短会话；
OneBot 链路断开时 QQ 账号可能仍在线，把它当会话真实结束会**系统性低估会话时长**；
反复抖动伪造大量「独立样本」，直接污染迁移前后比较。

修：账本边界用**已确认的**状态转换而非原始单拍；`LINK_DOWN`/`OBSERVER_DOWN`/unknown/数据不可用
一律按观察中断处理并至少标 `end_censored=true`，除非之后拿到明确的账号离线证据；
只有连续确认的 `AUTH_REQUIRED` 才算非删失 kicked 结束；原始采样与确认后区间都保留以便审计。

### F-07 为避免告警误报而折叠的 unknown 被纳入会话时长统计
`T3-design.md:312-326,789-807,841-859`｜核验点 12

设计正确要求 `account_online is None` 不产生离线告警，但同时把 unknown **折叠为 `AccountView.ONLINE`**；
账本又按 `== ONLINE` 开始区间，报告过滤只检查 `start_censored`/`end_censored`，
不过滤 `account_evidence != "online"`。

⇒ 启动后长时间只有 `account_online=None`，随后一次 auth-required 会被记成**非删失 kicked 区间**，
尽管该区间从未证明账号在线；unknown→online 的启动等待被算进会话长度；
`account_evidence` 是单个标量，表达不了区间中途由 unknown 变 online。

修：**告警视图与测量视图分开**。告警可继续把 unknown 当「不告警」，但统计区间只能从明确
`account_evidence=online` 开始；unknown 参与过的区间必须删失或排除；报告过滤须要求全段 confirmed-online。

### F-08 哨兵自身停机、采样缺口与 epoch 切换没有完整区间语义
`T3-design.md:768-789,801-812,825-832,974-975`｜核验点 12

未闭合区间放 `state.json`，但没定义哨兵停机数小时后首次采样如何处理缺口；`max_gap_s` 示例固定 60
却没规定如何检测超过一拍的缺口；epoch 变更时区间可能跨 `datacenter`/`home_broadband`，
而单条记录只有一个 `epoch` 字段，也没定义按开始 / 结束 / 切换时刻归类。

⇒ 哨兵停机期间 Hermes 仍在线，重启后读到 ONLINE 若直接续旧区间，未知的数小时被算成在线时长；
迁移当天改环境变量并重启 sentinel，旧区间可能被错归入新 epoch，污染前后对比。
`Persistent=true` 只补一次触发，不补齐停机期采样。

修：持久化 `last_sample_at`，缺口超过允许抖动即关闭旧区间为 `end_censored=true` 并新建
`start_censored=true` 区间；记录真实 `max_gap_s` 并为缺口写测试；
epoch 切换做成显式事务（先关闭 / 删失旧 epoch 活动区间再开新的），或按采样 epoch 切分、禁止跨 epoch。

### F-09 迁移门槛在迁移成功时可能永远无法满足，并产生选择偏差
`T3-design.md:862-873`｜核验点 13

要求迁移后仍须「≥7 天且 ≥10 段非删失区间」。**但如果家宽迁移确实改善了稳定性、账号连续在线超过
7 天，就不会产生 10 段已完成区间。** ⇒ 成功结果反而无法通过验收，只能继续等真实掉线；
为凑够 10 段而等待的样本天然偏向失败事件，不能代表稳定运行；
这会把「长时间没掉线」误当成「数据不足」，或诱使运维人为改变条件。

修：区分 pilot 门槛与最终统计结论。基线可要求 7 天 + 10 个完成区间；
**迁移后应允许「7 天观察期 + 全部右删失 / 零失败」进入预先定义的生存分析或置信上界判定**；
设最大等待期限，超期输出「无足够事件，但无观测到失败」，不得强行等到 10 次失败；
至少报告暴露时间、删失数、失败数，而不只报完成区间的中位数。

## 中

### F-10 `n < 10` 防呆没覆盖所有报告路径
`T3-design.md:834-859`

`--compare` 明确要求任一侧 `n < 10` 不下结论，但随后给出的「无 CLI 等价算法」会对任意非空样本
直接打印 median；单 epoch 的 `report` 也没禁止在 `n<10` 时展示可被当成结论的统计量。
⇒ 操作员用文档里的 Python 片段得到 `n=1` 的中位数，**重演 H1 §3 用 n=2 宣称固定会话寿命的错误**。
修：所有报告入口共用一个统计函数；`n=0..9` 一律输出「样本不足，不下结论」；删除或修正无 CLI 片段。

### F-11 去抖与冷却参数仍可能造成告警疲劳，消息预算未算完
`T3-design.md:351-384,397-406`

一次 9.7 / 11.7 小时 auth-required 周期 ≈ 首条 A1 + 第 1~6 小时各一条 + 恢复 1 条 ≈ **8 条**，
且文档没写清冷却窗口计数是否含首条（7/8 条歧义）。反复重启场景「10 分钟掉线 / 3 分钟在线」
可反复产生 A2+恢复对，全局上限仍允许 6 条/小时；若汇总消息不计入上限还可达 7 条/小时。
⇒ 持续抖动数天会稳定每小时打扰，用户关掉告警后会连真正的掉线一起错过。
修：给出明确时间线与计数定义；汇总消息计入全局上限；加 episode-level backoff；
恢复通知要求更长稳定期；把 9.7h / 11.7h / 反复重启序列写成状态机 golden tests。

### F-12 通知超时与每日心跳没有形成可执行契约
`T3-design.md:589-598,635-668,716-736,981-1035`

只规定了探针超时，**没规定 Telegram `urllib` 请求的超时**；`TimeoutStartSec=45` 是 systemd 杀进程上限
而非 HTTP 超时，也没说明被杀前告警状态是否已持久化；每日心跳只有常量，没定义调度方式、
夏令时 / 重复发送 / 错过窗口 / 发送失败的状态；测试也没验证「每日恰好一次」或发送阻塞行为。
⇒ Telegram API 或 DNS 阻塞时 oneshot 占住 timer 后被 systemd 终止，告警既没发出也没持久化 —— 静默。
修：加固定 `NOTIFY_TIMEOUT_SECS` 并保证总执行时间 < tick 间隔；明确持久化顺序、重试与幂等键。

### F-13 T3-B 的 hint 只在首次 A1 确认时获取，之后永久 unknown
`T3-design.md:435-466,1014-1018`

SSH hint 只在 A1 首次确认时执行一次，但 hint 最大年龄只有 900 秒。长时间掉线时：首次调用可能发生在
日志尚未出现短信验证标记时 → 之后 `login_hint.json` 更新为 `sms_verify` → sentinel 不再拉取 →
900 秒后本地 hint 过期 → 后续所有告警只能写 unknown。
⇒ **用户明明需要短信验证，却只持续收到泛化的「登录方式未确定」，T3-B 没有真正闭合短信验证问题。**
修：首次确认后按最小频率重新拉取（hint 过期时，或每个长冷却窗口最多一次）。

## 主线程复核（第二意见的第二意见）

对审计员三条关键事实断言做了独立代码核对，**全部证实**：

- **F-02 证实**：`tools/onebot_client.py::onebot_base_url()` docstring 原文
  「*Prefers `ONEBOT_HTTP_URL` and falls back to `ONEBOT_WS_URL`*」，实现先读 `ONEBOT_HTTP_URL`。
  ⇒ 环境里存在该变量时，「WS-only 到 127.0.0.1:3011」的声称不成立。
- **F-04 证实**：`gateway/status.py:1178-1188`，`recorded_start` / `current_start` 任一为 `None`
  即跳过比对直接 `return True`。⇒ start_time 缺失 + PID 复用 = 误判 writer 存活。
- **F-04b 证实**：`gateway/status.py:1716-1722`，`age = now - written_dt`，`return age > ttl_s`。
  未来时间戳 age 为负 ⇒ 判为不陈旧。

**严重度调整**：仅 F-03 降为「表述问题」，其余维持。
