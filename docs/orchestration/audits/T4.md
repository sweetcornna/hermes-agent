## 致命

### F1 NapCat 单元仍设计了自动重启
`T4:793-794,877-878,2293`（解释在 `:933-943`）｜硬约束 5

原生路径与 Docker 回退路径均用 `Restart=on-failure` / `RestartSec=45s`，附录还要求最后
`enable napcat-native.service`，机器重启后会自动启动 NapCat。`StartLimitBurst=1` 只限制单位时间内
启动次数，不等于 `Restart=no`。

修：删除 `Restart=on-failure`，改 `Restart=no`；不要 enable 开机自启；
把「人工重试」定义为唯一的 `reset-failed` + 手动 `start` 流程。

> **主线程复核：部分成立，严重度下调为「中」。**
> 审计员把 T5.md 硬约束 5「不得设计自动重启/自动重登/自动密码登录」读成了禁止 systemd 的
> `Restart=`。但那条约束针对的是 **watchdog 模式**（`napcat-watch.py`：检测异常 → `systemctl restart`），
> 而不是 unit 自身的重启策略。且 **H1 §10 恰恰建议**把 `Restart=always` 改成
> 「`on-failure` + 合理退避」。`StartLimitIntervalSec=3600` + `StartLimitBurst=1` 意味着
> **每小时至多一次自动重启**，之后进入 `failed` 且必须人工 `reset-failed`——这本身就是人工闸，
> 与硬约束 5 的意图一致。
> **保留的有效部分**：开机 `enable` 会在重启后自动发起一次登录尝试，这一点值得在 runbook 里
> 显式讨论取舍（机器重启后是让 QQ 自己回来，还是等人），而不是默认 enable。

### F2 发现已有 `ntqq/` 时要求移动、重建，甚至删除复制品
`T4:369-385`｜硬约束 2

新机 `/opt/napcat/ntqq` 非空时，runbook 建议 `mv` 到 `.bak-pre-T4-...` 再 `install -d` 新建空目录，
并写明如果是从别处复制来的就「删掉那个复制品」。**直接违反「设备身份目录绝不能删、复制到并行实例
或重建」。** 后果：真实设备身份被移出工作路径 → NapCat 生成新身份 → 变成一次未经批准的新设备认证；
删除复制品还会破坏取证与回滚材料。

修：新机只允许一种情况——经确认此前从未运行过 NapCat 且身份目录从未存在，此时创建空目录作为挂载点。
**目录非空必须硬阻断**，不得 `mv`/`rm`/重建；是复制品也只能隔离并报告。

### F3 §3.5 五条放行闸不可执行，且即使修正转义仍会漏检
`T4:597-604`（进程残留检查在 `:511-535`）｜硬约束 3

表格中管道符写成了字面反斜杠：`... && echo ALIVE \|\| echo DEAD`、`ss -ltn \| grep -c ...`、
`find ... \| wc -l`。这些在 Markdown 行内代码里，反斜杠不会被移除；复制执行时远端 shell 会把
`\|` 当字面字符而非管道运算符，`\|\|` 也不是 `||`。**预期的 `DEAD` 和 `0` 不会可靠产生。**

即便手工删掉反斜杠，第 3 行仍只跑 `pgrep -u napcat-native`，没有在最终闸门验证
`cornna-cn:127.0.0.1:3011` / `:6099` 无监听、完整进程树（`dbus-run-session → AppRun → qq → qq`）
不存在、其他用户或容器中的并行实例不存在——**与表格宣称的「无 QQ 进程、无监听」不一致**。
一个没有 `napcat-native` 用户进程但仍持有 3011/6099 的残留可以让闸门看起来通过，随后新机启动
就产生并行登录。

修：移到 fenced code block 用真正的管道；对 SSH 失败 / 命令不存在 / 权限不足分别报错，
任何检查失败必须阻断而非映射成安全状态；最终闸门同时检查完整进程树、3011、6099、容器和 cgroup；
用明确的 `if ...; then exit 1; fi` 而非依赖人工看管道输出。

> **主线程复核：完全成立。** 已核对 `T4:600-604`，`\|\|` 与 `\|` 确为字面反斜杠。
> 第 3 行确实只有 `pgrep`。这是本次审计里最具体、最可验证的缺陷。

### F4 native 路径的 `preflight` 在无法检查 Docker 时错误打印 `OK`
`T4:674-687,699-726`（服务调用在 `:790`）｜硬约束 3

`ExecStartPre` 在 `User=napcat-native` 下运行，而 T4 自己要求该用户**不能加入 `docker` 组**。
于是 Docker 存在但无权访问 socket 时，`docker ps` 失败、错误被 `2>/dev/null` 丢弃、
条件分支直接跳过，最后仍打印 `preflight: OK`。`ss` 不存在或检查失败时同样**失败开放**。

另：正常路径要求整份复制 `cornna-cn` 上的旧 `preflight`，只说「逐行读一遍并修改硬编码端口」，
没有实际修改命令，也没有验证复制后的脚本确实检查了 home 的 3001/6099；后续只验证脚本返回 `OK`，
没有验证检查行为。

修：把需要 root 的容器 / 全局进程 / 端口检查拆成 root-owned、只读、**失败关闭**的 helper；
不要把 `napcat-native` 加入 `docker` 组；对 `ss`/`docker ps`/`pgrep`/`flock` 的命令不存在、
权限错误、异常退出全部视为阻断；给出端口替换和行为测试，验证占用 3001/6099/Docker 容器/QQ 进程时
分别返回非零。

### F5 WebUI token 被命令明确打印到终端
`T4:1083-1093`｜硬约束 10

`sudo jq -r '.token // .webuiToken // empty' .../webui.json` 会把 token 值打到终端；
兜底建议 `sudo jq . webui.json` 还可能打印整个文件。违反「token / 密码 / cookie 的值不得出现在
文档、命令行或输出里」。⇒ shell scrollback、终端录制、审计采集或远程会话日志可能保存 token；
拿到它的人可以控制 WebUI（重启 QQ、改配置、发起登录）。这与文档他处「不把 WebUI token 发到聊天里」
自相矛盾。

修：只检查字段存在且非空（如输出 `WEBUI_TOKEN_PRESENT=true`）；要求操作者从受控密码管理器或
本地浏览器输入凭据；删除「打印 token 看一次」和「打印整个 webui.json」的兜底命令。

> **主线程复核：成立。** 文档确有 ⛔ 警告不要粘进聊天，但「打印到终端」本身就是硬约束 10
> 禁止的「输出」。

### F7 T4 的账本字段、marker 和报告 CLI 与 T3 设计不兼容
`T4:2005-2080,2039-2059`

T4 用 `env=cloud-aliyun-gz/home-residential`、`backend_host`、`egress_ip_changed`，执行
`report --group-by env`；而 T3 用 `epoch=datacenter/home_broadband`，接口是 `report --compare`

T4 追加的 marker 只有 `type`/`event`/环境字段/时间戳，没有 `schema`/`duration_s`/`epoch`。
⇒ `report --group-by env` 可能因未知参数直接失败；marker 直接追加进 session JSONL 可能被
ledger/report 当普通 session 处理。另：T4 只在正文说「迁移完成后同样追加 `t4_migration_done`」，
没给实际命令，**迁移窗口无法可靠闭合**。

不要手写 ledger 不支持的 marker 行；给出 begin/done 两条完整可验证命令。

### F8 watchdog 必须保持 masked，但 runbook 只验证一个服务是否 inactive
`T4:537-559`（当前事实见 `decisions.md:70-75`）

实测现状是 `napcat-watch.service`、`qq-watchdog.service`、`qq-watchdog.timer` **三者均 masked**，
而 `napcat-native-health.timer` enabled（只读探针，不负责恢复）。T4 把
`systemctl list-timers --all | grep -i -E 'napcat|qq' || echo NO_TIMERS` 的预期写成 `NO_TIMERS`，
**会把当前合法的 `napcat-native-health.timer` 当成不符合预期**；同时没有验证 `qq-watchdog.*`
是否仍为 masked。若 `napcat-watch.service` active，runbook 只执行 `disable --now` 而不再 `mask`，
`disabled` 仍可被手动启动或被依赖拉起。

修：明确区分允许的只读 health timer 与禁止恢复的 watchdog；逐个核对三件套均为
`inactive` + `masked`；允许 `napcat-native-health.timer` enabled 但检查其 ExecStart 不含恢复动作；
对 active watchdog 先 `disable --now` 再 `mask`，并验证 `is-enabled` 返回 `masked`。

### F9 Docker 回退路径挂载了错误的 config 目录，且会无备份删除容器
`T4:850-899`（native 配置写入位置见 `:966-1055`）

native 路径把 OneBot 配置写入 `/opt/napcat-native/config-candidate`，但 Docker unit 挂的是
`-v /opt/napcat/config:/app/napcat/config`，而 runbook 没有创建、填充或验证 `/opt/napcat/config`。
⇒ 回退路径下容器很可能用一个新建空目录，没有 OneBot token/host/port ⇒ 容器内 3001 不启动 ⇒
Hermes 握手失败 ⇒ 操作者可能误判成隧道故障并反复操作。

另：`ExecStartPre=-/usr/bin/docker rm -f napcat` 会在每次启动前删除同名已停止容器，
**没有先保存 inspect / 配置 / 状态证据**，违反破坏性步骤前备份要求，且把容器清理做成隐藏副作用。

修：统一 Docker 与 native 的配置源；回退路径单独定义并验证 config 目录 / owner / 权限 /
OneBot host/port/token；删除自动 `docker rm -f`，发现同名容器时先停止并阻断，要求人工确认后再处理。

### F10 §10 仍引用已明确不存在的 `napcat.service`
`T4:565-571`（当前事实声明在同文件 `:27-36`、`decisions.md:58-63`）

§0.1 明写当前 unit 是 `napcat-native.service`、`napcat.service` 在 `cornna-cn` 上不存在，
但 §10 又写「权威 `cornna-cn:napcat.service` 当前仍是 systemd `Restart=always`」。
⇒ 把维护者引向不存在的 unit，真正的 `napcat-native.service` 生命周期策略无人处理。
§10 对 `NAPCAT_QUICK_PASSWORD` 也没区分 active unit 实际读的 `/etc/napcat-native/env`
与 Docker 时代残留的 `/etc/napcat/napcat.env`。

修：§10 所有 `napcat.service` 改为 `napcat-native.service`；列出当前 unit 的实际 `Restart` 值
和实际 `EnvironmentFile`；残留文件单独标注，不得称为 active environment。

### F11 扫码后的 kicked 检查用 `|| true`，会把日志检查失败伪装成零次
`T4:1530-1545`

`sudo journalctl ... | grep -c -i -E 'kicked|KickedOffLine' || true`：`journalctl` 失败、
unit 名错误或日志不可读时，grep 得到空输入输出 `0`，`|| true` 再把失败状态吞掉。
⇒ 操作者看到 `0` 解释成「没有 kicked」，在没有真实日志证据的情况下继续迁移。

修：分离日志采集与匹配两个状态；先验证 `journalctl` 成功并得到有效日志，
再把「成功读取但无匹配」解释为 0；删除 `|| true`；把日志时间窗口和 unit 存在性作为硬闸门。

### F12 `napcat-native` 与 `obtun` 的创建顺序不可执行
`T4:369-390,1131-1140`

§2.4 先 `install -d -o napcat-native -g napcat-native /opt/napcat/ntqq`，之后才 `useradd`；
用户和组尚不存在时 `install` 会失败。隧道部分先 `install -d -o obtun -g obtun /etc/onebot-rtunnel`，
但 `obtun` 的创建只埋在后面的括号说明里，且没明确创建私有组。
修：先创建并验证用户和组再创建目录；用 `--user-group` 或先建组；给出 `id` / `getent group` 预期输出。

### F13 `egress_ip_changed` 只有脚本，没有 timer 或账本集成
`T4:2039-2059,2294-2295`

只给了 `/usr/local/sbin/t4-egress-log`，然后说「用 systemd timer 每 5 分钟跑一次即可」，
没有 service/timer/安装/启用/权限/验证/回滚。脚本在无法访问 `ipinfo.io` 时

⇒ 无法区分「没换 IP」和「根本没采集成功」，迁移后统计不能排除家宽重拨这一混杂因素。
修：提供完整 service/timer；采集失败返回可诊断的非零状态或写入明确的 `unknown`；

### F14 多个破坏性动作没有在动作前备份
`T4:2005-2021`（marker）、`:613-638`（防火墙）｜硬约束 11

marker 先 `tee -a sessions.jsonl` 和全文件 `sed -i`，之后才在说明里给 `cp -a ...bak`；
按代码块顺序执行等于改完才备份。`sed -i` 还会重写整个 JSONL，不符合 T3 的 append-only 约束。
UFW 三条命令之前没有保存现有 firewall 状态或回滚材料——通过 SSH 操作新机时可能直接切断管理连接。
修：先算 timestamp 并完成备份再追加 marker；直接生成完整 timestamp 后一次追加一条合法 JSON，
不用 placeholder + `sed`；启用 UFW 前保存 `ufw status numbered` 与当前 SSH 放行状态并给出恢复步骤。

### F15 `permitlisten` 验证命令遗漏 `ExitOnForwardFailure=yes`
`T4:1167-1174`（该选项重要性的说明在 `:1343-1344`）

验证 `permitlisten` 时跑 `ssh ... -N -R 127.0.0.1:9999:127.0.0.1:22 ...` 却没加
`-o ExitOnForwardFailure=yes`——而 T4 自己已说明没有该选项时远程转发失败 SSH 可能保持 active。
另：9999 是否已被占用没有预检。⇒ 验证命令挂住，或把「SSH 仍 active」误当成限制生效。
修：加 `-o ExitOnForwardFailure=yes -o ConnectTimeout=10`；用事先确认未占用的临时端口并用
`timeout` 包住；同时检查退出码和远端端口是否确实没有监听。

### F16 §6.6 在 Hermes 已 active 时重复建立额外 OneBot WebSocket
`T4:1767-1775`（依据 `T3-design.md:199-216,927-928`）

§6.6 先启动 Hermes，然后每分钟跑一次独立的 `onebot_probe.py`——这会在持久 Hermes WS 之外
再建立六条短生命周期 WS。虽然动作是只读，仍违反「避免第二条连接」的设计边界。
⇒ 后端连接槽位或事件顺序竞争；读到的是额外连接的状态而非 Hermes 实际使用的连接状态。
修：需要 `get_status`/`get_login_info` 的短探针**在 Hermes 启动前**执行；
Hermes 启动后只读 runtime state 和进程级指标。

> **主线程注**：这与 T3 审计的 F-01 是同一类错误（在 Hermes 活着时开第二条连接）。
> 两份设计各自独立犯了同一个错，说明这条铁律需要在两边都写成可测试的断言，而不是口头约定。

## 主线程复核

- **F3 完全成立**：核对 `T4:600-604`，`\|\|` 与 `\|` 确为字面反斜杠；第 3 行确实只有 `pgrep`。
  这是本次审计最具体、最可验证的缺陷。

- **F1 严重度下调为「中」**：审计员把硬约束 5 读成禁止 systemd 的 `Restart=`，但该约束针对的是
  watchdog 模式（检测异常 → `systemctl restart`），而 H1 §10 恰恰建议 `on-failure` + 退避；
  `StartLimitIntervalSec=3600` + `StartLimitBurst=1` 意味着每小时至多一次自动重启且之后必须人工
  `reset-failed`，这本身就是人工闸。保留的有效部分是「开机 enable」的取舍需要显式讨论。

  说明这条铁律必须在两边都写成可测试断言，不能停在口头约定。
