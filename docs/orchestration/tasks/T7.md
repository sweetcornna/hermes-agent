# T7 — 主窗口结构性豁免入站限流

## 背景（你没有我的上下文，全部读完再动手）

仓库 `/Users/cornna/project/hermes-agent`，分支 `feat/corlinman-migration`。
QQ 通过 OneBot v11 接入。有四套限流开关，当前**全部默认 0（关闭）**，我们准备逐步打开其中
真正 group-scoped 的三个。但打开之前必须先修掉一个结构性缺陷。

## 缺陷

`plugins/platforms/onebot/router.py:293-335`：两个限流器跑在私聊/群聊分支**汇合之后**，
且**没有任何 `is_group` 条件**：

```python
if self.group_limiter is not None:
    if not self.group_limiter.check(f"{binding.channel}:{binding.thread}"):
        self._fire_hook(binding.channel, "group"); return None
if self.sender_limiter is not None:
    key = f"{binding.channel}:{binding.thread}:{binding.sender}"
    if not self.sender_limiter.check(key):
        self._fire_hook(binding.channel, "sender"); return None
```

⇒ 名为 "group" 的桶**同样在限私聊**，超限时静默 `return None`。

后果：**主窗口是唯一的网关控制通道**（QQ 号 `2104743984` 的私聊；提醒、命令全走这里，
群永远不是控制台）。一旦主窗口被限流静默丢弃，运维就失去了唯一的带内控制入口——
而且是静默失败，看不出来。

## 要做的

1. 让**主窗口私聊结构性豁免**入站限流：`group_limiter` 与 `sender_limiter` 都不得作用于主窗口。
   「结构性」= 不是靠配置调大阈值，而是代码路径上根本不进桶。
2. 主窗口的识别**复用现有实现**——`plugins/platforms/onebot/main_window.py` 已有相关逻辑，
   先读它，用它暴露的判定函数/常量，**不要新造一套 ID 判定或硬编码号码**。
   如果它没有可直接复用的判定入口，就在 `main_window.py` 里加一个语义明确的公开函数，
   由 `router.py` 调用；不要把判定逻辑抄进 router。
3. 顺带评估：`group_limiter` 这个名字对非主窗口的普通私聊是否也应加 `is_group` 条件。
   **不要顺手改**——在结果文件里写清楚你的判断和理由，交给主线程决定。本次只改主窗口豁免。
4. 静默丢弃的可观测性：豁免生效后主窗口不再受影响，但普通会话被限流仍是静默的。
   在**不改变现有行为**的前提下，确认 `_fire_hook` 是否已经足够暴露这件事；
   不够的话在结果文件里提出建议，同样不要顺手改。

## 硬约束

- **只改这一件事。** 不重构限流器、不改阈值默认值、不动 `rate_limit.py` 的实现。
- 改动前先 `git stash list` 与 `git status` 确认工作区状态，不要覆盖别人的未提交改动。
- **必须补测试**，放在既有测试文件的惯例位置（先找 `tests/gateway/test_onebot_router.py`
  和 `tests/gateway/test_onebot_rate_limit.py`）。至少覆盖：
  主窗口私聊在两个限流器都开且已超限时**仍然通过**；非主窗口会话行为不变。
- 跑测试前先做 **stash 基线对照**：本机存在与本改动无关的恒红用例，
  必须先记录基线红名单，再对比，**不得把恒红当成自己引入的回归，也不得用它掩盖真回归**。
- 不碰生产，不 SSH，不改任何 `.env` / `config.yaml` / 部署文件。
