# T3 — QQ 掉线告警通道：设计

轨道/档位：Claude / opus（需要设计判断；隐性约束多，且有一条明确的「不许做什么」的历史教训）

## 背景（自包含，你看不到主线程上下文）

仓库 `/Users/cornna/project/hermes-agent`。Hermes 通过 `plugins/platforms/onebot/` 接一个
**个人 QQ 号**（`2952532060`），经 NapCat 的 OneBot v11 正向 WebSocket。

### 当前的设计缺口

适配器**刻意不做**扫码登录和后端生命周期管理（`plugins/platforms/onebot/README.md` 的
「故意不实现」清单里明写）。账号被踢下线时，适配器只做三件事：把账号状态置为 `auth_required`、
拒发一切出站消息（`retryable=False`）、写一条 WARNING 日志。

**结果是「只有停手，没有告警」**：`docs/migration-corlinman/H1-napcat-hardened.md` §3 记录，
两次掉线的空窗分别是 **9.7 小时和 11.7 小时**，全在等人自己发现。

### 一条不能违反的历史教训

曾经有一个 `/usr/local/sbin/napcat-watch.py` 在检测到异常时直接
`systemctl restart napcat.service`。它已于 2026-08-30 被**有意 stop/disable**，理由记在
H1 §8.4：它是**第二个会消耗登录尝试的生命周期管理器**。反复的自动重启/密码登录会让腾讯风控
进一步加码，被踢后密码登录还会阻塞在短信验证上。

**所以本任务要设计的是纯告警，不是自动恢复。** 任何「顺手把它重启一下」的设计都是错的。

## 目标

设计一条 QQ 掉线告警链路，写成设计文档。**本任务只出设计，不写实现代码。**

## 已知的可复用材料（自己去代码里确认，不要照抄这段）

- 适配器的 `health_snapshot()` 方法返回 `link_online` / `account_online` / `account_state` /
  `account_auth_required` / `last_heartbeat_at_ms` / `heartbeat_age_seconds` 等字段。
  在 `plugins/platforms/onebot/adapter.py` 里找到它，确认真实字段名和语义。

  监听 `127.0.0.1:1080`），因为 `api.telegram.org` 在生产机上被墙。
  `TELEGRAM_BOT_TOKEN` 在 `/opt/hermes/data/.env`，告警收件人 chat_id 是 `1114483029`。
- 告警**必须走 Telegram，不能走 QQ** —— 需要告警的时候 QQ 正好是死的。

## 设计必须回答的问题

1. **触发条件**：哪些状态该告警？至少要覆盖 `account_auth_required` 和链路长时间静默。
   注意区分：链路静默是瞬时故障（会自愈，不该吵人），账号 auth_required 才是需要人来的。
   `account_online` 为 `None`（后端从不报状态）**不能**当离线——会误报到爆。
2. **去抖**：不能一掉线就狂发。要有连续 N 拍确认 + 冷却窗口。给出具体数字和理由。
3. **恢复通知**：账号回来了要不要发一条？给出判断。
4. **短信验证的特殊处理**：被踢后 NapCat 日志里会出现
   `https://ti.qq.com/safe/tools/captcha/sms-verify-login?...`。这种情况必须**明确告诉人
   「需要你拿手机过短信验证」**，而不是发一条泛泛的「QQ 掉线了」。
5. **落点选择**：这个告警器应该住在哪？给出方案并说明理由与取舍。至少要评估：
   - 做成 Hermes 插件内的一个后台循环
   - 做成生产机上独立的 systemd timer（像被下线的那个 watchdog 一样，但只读）
   两者在「Hermes 自己挂了谁来告警」这个问题上表现不同，这一点必须讨论到。
6. **权限边界**：设计里要有一条明确的、可被审计检查的约束 ——
   **这个组件不得拥有任何重启容器 / 触发登录 / 调用 NapCat WebUI 写接口的能力。**
   把这条写成可验证的形式（例如「它能调用的接口白名单是……」）。
7. **测试方式**：怎么验证它？注意 —— **不许真的把 QQ 弄掉线来测**。
   仓库里已有的做法是打桩（覆盖 WS URL 指向死端口、状态文件指临时目录、发送函数打桩）。
   给出可执行的验证方案。
