# T1 — account-state 加固：完整性核对与可部署清单

轨道/档位：GPT / gpt-luna-exec（规格明确、照章核对，不需要设计）

## 背景（自包含，你看不到主线程上下文）

仓库 `/Users/cornna/project/hermes-agent`，分支 `feat/corlinman-migration`，工作区有大量未提交修改。

Hermes 通过 `plugins/platforms/onebot/` 适配器接一个**个人 QQ 号**（经 NapCat 的 OneBot v11
正向 WebSocket）。这条链路有一个关键设计：**传输在线 ≠ QQ 账号在线**。WS 握手成功只证明
NapCat 可达，不证明 QQ 登录着。适配器为此维护了独立的账号状态机
（`unknown` / `online` / `auth_required`）。

生产事故背景：QQ 号被腾讯踢下线后，如果 Hermes 只看到「链路在线」就继续尝试发消息，
会让风控进一步加码。所以账号状态机是**风控安全设施**，不是可选优化。

**问题**：运维文档 `docs/migration-corlinman/H1-napcat-hardened.md` 的 §7.4 和 §10 记录，
生产机上跑的 `/opt/hermes/repo` 停在 commit `8911e2e0edf750b104edbdc106d63d6cdac88524`，
其中的 OneBot adapter/client 与本地工作区哈希不同，**不含**本地的三项加固：

- `ACCOUNT_AUTH_REQUIRED_MARKER`
- `account_probe_secs`
- 独立 account-state 追踪

H1:573 原文：「账号被踢时远端 Hermes 仍可能只看到 link 层在线」。

## 目标

产出一份**可直接照做的部署清单**，让人能把这三项加固安全地推上生产。你**不部署**，只核对与整理。

## 具体要做的事

1. 读 `docs/migration-corlinman/H1-napcat-hardened.md` 的 §7.4（约 267-273 行）和 §10（约 566-576 行），
   把它列出的远端落差逐条抄下来。
2. 在本地代码中定位这三项加固的**全部**落点。至少要 grep：
   `ACCOUNT_AUTH_REQUIRED_MARKER`、`account_probe_secs`、`ACCOUNT_PROBE_SECS`、
   `_probe_account`、`_set_account_status`、`account_auth_required`、`_publish_account_runtime_status`、
   `set_account_status_callback`、`_absorb_status`。
   涉及文件预期在 `plugins/platforms/onebot/adapter.py` 和 `plugins/platforms/onebot/client.py`，
   但**你要自己确认**，不要假设只有这两个。
3. 跑测试并**如实记录输出**：
   `python -m pytest tests/gateway/test_onebot_auth_state.py -q`
   如果有失败，**先做基线对照**：`git stash && python -m pytest ... -q; git stash pop`，
   判断是本次相关的回归还是本机恒红的既有失败。两次输出都要记进结果文件。
4. 产出部署清单：逐个文件写明「文件路径 / 这个文件带来什么加固 / 不部署它的后果」。
   注意生产上这些文件是 **untracked（`??`）**、靠 scp 覆盖部署的，不能 `git pull`，
   所以清单要按**文件**组织，不是按 commit。
5. 检查这三项加固之间有没有**部署顺序依赖**（例如 adapter 依赖 client 新增的回调签名）。
   如果有，明确写出必须一起部署的文件组；如果没有，也要明确写「无顺序依赖」。
