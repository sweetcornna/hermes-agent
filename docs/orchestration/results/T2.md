## 1. 实现语义与代码行号

实现文件均为任务指定的只读核对对象；本任务没有修改

### 1.1 `ONEBOT_RATE_LIMIT_GROUP_PER_MIN`

- **它限的是什么**：这是入站路由闸，不是出站消息计数。适配器从
  `rate_limit_group_per_min` 读取 YAML 值，缺省时回退到
  `ONEBOT_RATE_LIMIT_GROUP_PER_MIN`，缺省值为 `0`
  （`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/adapter.py:1640-1646`）。
  值大于 0 时，适配器创建 `TokenBucket.per_minute(group_per_min)`
  (`adapter.py:1672-1674`)。
- `TokenBucket.per_minute(n)` 的容量是 `n`，每秒线性回填 `n/60`
  (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/rate_limit.py:70-74`)；
  `check()` 每放行一次消耗一个 token，新 key 初始满桶
  (`rate_limit.py:81-103`)。因此它是**每个 conversation thread 的入站突发预算**，
  不是精确的“最近一分钟恰好 N 条”硬窗口。
- 路由器在群主开关、白名单、提及/关键词/冷却和空文本检查之后才执行这个桶
  (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/router.py:293-325`、
  `router.py:325-330`)；被前面过滤掉的消息不会消耗它。
- 在群聊里 key 是 `channel:thread`，其中 `thread` 是群 id；所以群聊语义是**每群**。
  但这段检查没有 `is_group` 条件，私聊也走同一段通用逻辑；私聊的 `thread` 是对方
  QQ id (`router.py:131-140`、`router.py:327-335`)。因此按当前代码，它在私聊中实际是
  **每个 DM 对话**的入站桶，名称里的 “group” 不是“仅群聊”的保证。
- **`0` 的语义**：代码级确认是关闭，而不是全部拒绝。适配器只有在
  `group_per_min > 0` 时才传入 `TokenBucket`，否则传 `None`
  (`adapter.py:1640-1646`、`adapter.py:1672-1674`)；`router.py:327` 对 `None`
  不检查。因此 `0` 不拒绝任何消息，也不记录桶状态。
- **@提及能否绕过**：不能。提及只影响前面的显式召唤/回复策略；令牌检查仍在
  `router.py:325-330` 无条件执行。@ 可以绕过群回复冷却，但不能绕过这个入站桶，且仍受
  群总开关和白名单约束。
- **与主动发言是否共用预算**：不共用。主动发言使用适配器的群 speech cap
  (`group_speech_allowed`)，而不是 `ChannelRouter` 的入站 `TokenBucket`
  (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/proactive.py:1181-1185`、
  `proactive.py:1446-1456`)。

### 1.2 `ONEBOT_RATE_LIMIT_SENDER_PER_MIN`

- **它限的是什么**：同样是入站路由闸。适配器从
  `rate_limit_sender_per_min` 读取 YAML 值，回退环境变量
  `ONEBOT_RATE_LIMIT_SENDER_PER_MIN`，缺省为 `0`
  (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/adapter.py:1647-1652`)；
  大于 0 时创建每分钟令牌桶 (`adapter.py:1672-1675`)。
- 路由器的 key 是 `channel:thread:sender`
  (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/router.py:331-335`)。
  因此群聊是**每群内每个发送者**的入站突发预算，不是跨所有群的全局“每人”预算；私聊
  因为 thread 和 sender 都是同一位 DM 对方，实际是该 DM 对话的发送者桶。
  令牌桶的容量、连续回填和非精确滑窗语义同上 (`rate_limit.py:70-103`)。
- 它只在前置回复闸通过后扣 token (`router.py:325-335`)，所以它限制的是“会进入后续
  模型/回复流程的入站事件”，不是已经发出的 QQ 消息。
- **`0` 的语义**：关闭，而不是全部拒绝。适配器在 `sender_per_min > 0` 时才构造桶，
  否则为 `None` (`adapter.py:1647-1652`、`adapter.py:1672-1675`)；关闭时没有检查、
  没有拒绝、没有记录。
- **@提及能否绕过**：不能。@ 不会跳过 `sender_limiter.check()`
  (`router.py:331-335`)。
- **与主动发言是否共用预算**：不共用；主动发言不经过这个入站 sender bucket，
  只会使用下面的群出站 speech cap。

### 1.3 `ONEBOT_GROUP_REPLY_COOLDOWN_SECS`

- **它限的是什么**：这是群内**反应式出站回复机会**之间的最小间隔，按群维度，
  不是每人维度，也不是入站消息总量限制。适配器从 YAML 的
  `group_reply_cooldown_secs` 读取，回退 `ONEBOT_GROUP_REPLY_COOLDOWN_SECS`，缺省为
  `0.0` (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/adapter.py:1615-1621`)，
  再传给 `ChannelRouter` (`adapter.py:1663-1671`)。
- 路由器只对已经通过群总开关、白名单和回复策略的**非显式召唤**消息比较
  `time.monotonic()` 与该群的上一回复时间 (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/router.py:357-381`)。
  它是一个“上次时间 + 最小 gap”的礼貌闸，不是令牌桶，也不是 N 条/M 分钟滑动硬窗口。
  未命中关键词/策略的消息不会更新时钟。
- **`0` 的语义**：关闭，而不是全部拒绝。实际条件是
  `if self.group_reply_cooldown_secs > 0` (`router.py:376-379`)；为 0 时不做时间比较，
  命中的非 @ 消息可以正常继续。
- **@提及能否绕过**：能（在群总开关和白名单已经通过的前提下）。显式消息直接更新该群
  时钟并返回 `True` (`router.py:363-365`)，显式消息包括 @ 提及；所以 @ 不受这个
  cooldown 限制且会重置它。这里的 @ 绕过不等于绕过其他限流器。
- **与主动发言是否共用预算**：不共用。这个时钟保存在 `ChannelRouter` 的
  `_last_group_reply_mono` 中，只约束反应式非 @ 路径；主动发言有自己的主动发言间隔，
  不读这个 cooldown。两者仍共同受下一节 speech cap 约束。

### 1.4 `ONEBOT_GROUP_RATE_LIMIT_WINDOW_MINUTES` + `ONEBOT_GROUP_RATE_LIMIT_MAX_MESSAGES`

- **它限的是什么**：这两个键组成群机器人的**出站 speech hard cap**，按
  `instance_id:group_id` 的每群预算，不按发送者计数。适配器把 window 分钟转成秒并读取
  max 值 (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/adapter.py:1622-1638`)。
- 它使用 `SlidingWindowCounter`，语义是精确的 trailing window：某条记录在
  `t + window_secs` 才失效，因此“3 分钟 5 条”不是令牌桶，也不会因为长时间安静而
  积累出一整桶突发 (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/rate_limit.py:152-157`、
  `rate_limit.py:164-201`)。
- 适配器使用模块级 `_GROUP_SPEECH`，key 由 `speech_key()` 生成
  (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/adapter.py:228-238`、
  `adapter.py:251-270`)。在反应式路径中，它位于命令短路之后、模型调用之前，且只对
  群聊的非 command 路由执行 (`adapter.py:2827-2841`)；命中后静默返回并记录
  `group_window` (`adapter.py:2842-2849`)。所以它是出站发言预算的预留/扣除闸，不是
  入站群消息计数器。
- **`0` 的语义**：任一项为 0 都是关闭，而不是全部拒绝。`SlidingWindowCounter.allow()`
  明确规定 `window_secs <= 0` 或 `max_count <= 0` 时直接返回 `True` 且不记录
  (`rate_limit.py:178-201`，特别是 `189-195`)；适配器两项缺省也都是 0
  (`adapter.py:1622-1638`)。
- **@提及能否绕过**：不能。适配器注释和条件都明确是“@mention does NOT bypass”，
  群 speech cap 的条件是 `not routed.is_command` (`adapter.py:2831-2836`)。@ 是
  mention，不是 command，因此仍消耗/受该群 hard cap。若显式启用了群命令控制，真正的
  slash command 会走 command short-circuit；这不改变 @ 的结论。
- **与主动发言是否共用预算**：共用，而且是同一份进程级滑动窗口。适配器文档说明该
  budget 对反应式和主动发言共享 (`adapter.py:231-238`、`adapter.py:264-270`)；主动
  路径先用 `record=False` 预览 (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/proactive.py:1181-1185`)，
  实际发出后用同一个 `_GROUP_SPEECH.record(key)` 记账
  (`proactive.py:1446-1456`)。因此主动消息会占用反应式回复的 5 条预算，反之亦然。

## 2. 推荐值与理由

推荐值已写入配置样板的 `platforms.onebot.extra`。样板当前
`group_replies_enabled: false`，所以群链路仍保持默认静音；这些值是打开群回复时使用的
安全配置，不会改变该总闸本身。对应配置行见
`/Users/cornna/project/hermes-agent/docs/migration-corlinman/B3-hermes-config.yaml.example:219-236`。

| 环境变量 | YAML `extra` 键 | 推荐值 | 理由 |
|---|---|---:|---|
| `ONEBOT_RATE_LIMIT_GROUP_PER_MIN` | `rate_limit_group_per_min` | `30` | 群级入站桶允许多个成员的正常消息，又能拦住整群刷屏；30 是容量也是每分钟回填，不把它误当成出站频率控制。 |
| `ONEBOT_RATE_LIMIT_SENDER_PER_MIN` | `rate_limit_sender_per_min` | `10` | 单个发送者每分钟 10 条足够覆盖正常对话，同时比群总桶更早拦截单人连发。当前代码把该桶也用于 DM，因此不取过低值；低频主窗口正常使用不会触发。 |
| `ONEBOT_GROUP_REPLY_COOLDOWN_SECS` | `group_reply_cooldown_secs` | `20` | 非 @ 回复至少相隔 20 秒，避免连续回复看起来像机器人；该值与迁移资料记录的 corlinman 生产默认一致，且不限制私聊。@ 被召唤时仍可即时回答。 |
| `ONEBOT_GROUP_RATE_LIMIT_WINDOW_MINUTES` | `group_rate_limit_window_minutes` | `3` | 与 max 配套形成精确滑动窗口，限制的是机器人在单群的总出站量。 |
| `ONEBOT_GROUP_RATE_LIMIT_MAX_MESSAGES` | `group_rate_limit_max_messages` | `5` | 3 分钟最多 5 条，平均约 1.67 条/分钟；它覆盖反应式与主动发言并防止安静很久后的突发倾倒。 |

### 关于主窗口私聊的边界

当前 `ChannelRouter.dispatch()` 的两个 token bucket 检查位于私聊/群聊分支之后的公共路径
(`router.py:293-335`)，所以 `rate_limit_group_per_min` 和
`rate_limit_sender_per_min` 并非严格的“仅群聊”开关。推荐的 30/10 是在**不改代码且
不把低频主窗口限死**的约束下取的宽松安全值：正常 DM 远低于 10 条/分钟，且 cooldown
与 speech cap 本身只作用于群。

如果未来的要求是“DM 绝对不受这两个 token bucket 影响”，仅靠当前配置无法实现，必须
把 limiter 检查显式包在 `binding.is_group` 条件中；本任务禁止修改 `router.py`，因此没有
越界做该代码改动。

### 是否同意 3 分钟 / 5 条

**同意。** 代码头注释明确把 `SlidingWindowCounter` 设计为群发言 cap，并说明令牌桶会在
长时间安静后放出整次突发 (`/Users/cornna/project/hermes-agent/plugins/platforms/onebot/rate_limit.py:6-12`)；
适配器又明确要求该预算跨反应式和主动发言共享 (`adapter.py:231-238`)。测试以
`window=180.0, cap=5` 验证生产形状，并在第一条记录满 180 秒后释放
(`tests/gateway/test_onebot_rate_limit.py:141-149`)。这正好同时满足账号安全和“群一旦打开，
发言频率像人而不是机器人”的目标，故保留生产值而不改成令牌桶或更宽松的上限。
