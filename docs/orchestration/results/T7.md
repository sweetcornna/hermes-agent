## 第 3 点判断：普通私聊是否应受 `group_limiter`

**判断：从现有命名、文档与 key 语义看，`group_limiter` 应在后续独立变更中加 `binding.is_group` 条件，只作用于群；本次按要求不改。**

理由：

1. 配置键和 README 都把它描述为 `rate_limit_group_per_min` / “per group”，而普通私聊没有 group 维度。
2. 私聊中 `binding.thread == binding.sender == 对方 QQ id`。因此 group key `channel:thread` 与 sender key `channel:thread:sender` 都退化成同一位 DM 对方的每会话预算；两个桶叠加时，较低阈值的 sender 桶通常已经覆盖实际约束，group 桶不再表达“群总量”。
3. 真正需要“所有会话共享的入站预算”时，当前 key 也做不到，因为它仍按每个 DM peer 分桶；若这是产品意图，应明确重命名/重定义为 conversation limiter，而不是继续让 `group` 名称与行为分裂。
4. 改成 group-only 会放宽普通 DM 行为，属于独立兼容性决定。T7 的任务边界只允许主窗口豁免，因此保留普通私聊现状并用参数化测试锁住。

建议主线程另开小任务：先确认普通 DM 是否只保留 `sender_limiter`，再增加 `binding.is_group`，同步 README 与测试；不要混入本次安全修复。

## 第 4 点判断：静默丢弃可观测性

**判断：`_fire_hook` 足以证明“进程日志里有一次限流丢弃”，但不足以作为完整的生产可观测性。**

现状证据：

- `router.py:360-365` 每次 group/sender 限流丢弃前都会调用 hook，且吞掉观察层异常，保证观察失败不影响聊天路径。
- `adapter.py:1677` 总是把 hook 接到 `_on_rate_limited`；`adapter.py:2539-2540` 以 INFO 记录 `OneBot: dropped an inbound message (<reason> rate limit)`。
- 所以对查看完整 INFO 日志的人而言，它不是完全不可见；聊天侧仍按既有行为不回复。

不足：

1. hook 只有 `(channel, reason)`；当前日志没有 thread/group、sender、实例或累计次数，无法定位哪个普通会话被丢弃。
2. 只有逐条 INFO 日志，没有结构化 counter、事件或告警出口；日志级别/采集策略变化后可能看不到，也无法直接回答“过去一段时间丢了多少”。
3. 在真正刷屏时逐条日志本身会产生噪声，却仍不能给出聚合态势。

建议后续在**不改变聊天侧静默行为**的前提下，增加按 `reason` 和会话范围聚合的 counter/metric，并发出限频的 WARN 汇总（例如时间窗内抑制数量）；若需要定位，扩展 hook 上下文携带 session/thread 与 sender。不要让观测失败成为 dispatch 的阻断条件。T7 不顺手实现。
